# Interface language: Tiếng Việt / English

Owner, 2026-11-24: "toàn bộ giao diện phải là tiếng Anh, kể cả giải thích, vì tao đang think in English … tốt nhất là
cho toggle giữa tiếng Việt / tiếng Anh". Vietnamese stays the default and stays exactly as it was; English mode shows
every text in English.

## 1. How it works

- **Vietnamese is the source.** Every interface string is written in Vietnamese in the code, as before. The string
  itself is the key of the English dictionaries (`src/i18n/en/<bundle>/<area>.ts`, `'Vietnamese': 'English'`).
- **The setting**: `Settings.lang` (`'vi'` default, `'en'`), synced like the other settings. The switch is in the shell
  (`LangSwitch` in `AppNav`: sidebar head and mobile top bar) and in Cài đặt → Hiển thị.
- **Elements translate themselves.** The app's JSX runs through `src/i18n/jsx-runtime.ts` (a resolver in
  `vite.config.ts` points React's JSX runtime there for the app's own files). In English mode every host element
  (`<p>`, `<button>` …) and fragment sends its string children and its text attributes (`title`, `aria-label`,
  `placeholder`, `alt`, `label` …) through the dictionary. So a label typed in JSX, a label from a table of constants
  (`ROUTES`, `ACTIVITIES` …) and a `vi` field of the content all come out in English **with no call at the site**, as long
  as the whole string that reaches the element is a dictionary key. In Vietnamese mode this step does nothing.
- **`tr(text)`** (`src/i18n`): the same lookup as a function, for text that does not pass through an element as a whole
  string: canvas / 3D text, `document.title`, `window.confirm`, a string that is cut up or parsed before it is shown
  (lesson markup), a label put inside another string.
- **``tl`…${x}…` ``**: the tag for a Vietnamese sentence with values in it. Its key is the text with `{}` for each
  value (`` tl`Còn ${n} thẻ` `` → `'Còn {} thẻ'`); the English uses `{0}`, `{1}` … in any order, and `{0|card|cards}` for
  a plural: `'Còn {} thẻ': '{0} {0|card|cards} left'`. Values that are Vietnamese labels are translated first. In
  Vietnamese mode the tag returns exactly what the plain template literal would.
- **A noun after a number in JSX** (`{n} câu`): the entry `'câu': '{#|sentence|sentences}'` agrees with the number
  just before it (the plural form when there is none).
- **`data-vi`** on an element keeps its text as written (the learner's own text, a Vietnamese example).
- **`getLang()`** for the rare logic that must differ (date and number formats, the order of a sentence built from
  parts).
- A switch remounts the shell (`key={lang}` in `App.tsx`), so nothing computed in the old language stays on screen.
  A string computed when a module loads is computed before the language is known: keep such constants in Vietnamese
  (plain strings, no `tl`) and let the element or `tr` translate them when shown.
- The dictionaries are separate chunks (`en-ui`, `en-content`, `en-town`), loaded only in English mode
  (`src/i18n/load.ts`): `ui` and `content` before the first render, `town` with the town page. The service worker
  caches them on first use. A string without an entry is shown in Vietnamese (never an error);
  `window.i18nMisses()` in the dev server lists the ones seen on screen.

## 2. The tool: `scripts/i18n-scan.mjs`

```
node scripts/i18n-scan.mjs                      # per area: strings, and how many have no English
node scripts/i18n-scan.mjs --areas              # which source files belong to which dictionary area
node scripts/i18n-scan.mjs --tag                # tag every untagged Vietnamese template literal with tl
node scripts/i18n-scan.mjs --todo <area> <todo.json>               # the strings of an area without English
node scripts/i18n-scan.mjs --apply <area> <todo.json> <answers.json>   # answers: { "<id>": "English", … }
```

`--apply` writes `src/i18n/en/<area>.ts` and regenerates the bundle files (`en/ui.ts` …). A dictionary file may also
be edited by hand (fix an entry, add one). `areaOf` in the script maps a source file to its area; `ui/common` holds
the words many pages share (written first, so every page uses the same English for them).

`src/i18n/coverage.test.ts` fails when a Vietnamese string in the code has no English entry (except in the areas it
lists as pending), when a template is not tagged, or when two bundles disagree about one string.

## 3. Rules for the English

- Natural, short, the voice of a modern learning app. Translate the meaning, not the words. Sentence case
  ("Listen again", not "Listen Again"). No exclamation marks the Vietnamese does not have.
- Keep to the glossary below and to `ui/common`. The app's name stays "Nghe Nối Âm".
- The honesty rules of docs/progress-report.md §6 hold in English too: hedge small samples, never promise
  native-like listening, "self-rated" for "tự đánh giá".
- The English being taught (example words, sentences, respellings like `KER-nəl`) is not touched.
- An entry must be right wherever the same Vietnamese string appears (keys are global in a bundle). A fragment of a
  sentence broken by a value (`Còn <b>{n}</b> thẻ`) gets an English fragment that is right on its own; when English
  needs another word order, turn the sentence into one `tl` template in the code instead.
- Never change a Vietnamese string to make a key: wrap, tag or restructure around it so that Vietnamese mode shows
  exactly what it showed before.

## 4. Meanings of the English sentences (`vi` fields)

The content gives each English sentence, phrase and story line a Vietnamese meaning, and many checks are "hear it,
then pick the meaning". In English mode a meaning is a plain-English paraphrase that does not reuse the key words of
the line where it can be avoided (so the check is still about understanding, not about matching sounds to
spelling). They are ordinary dictionary entries keyed by the Vietnamese meaning.

Done 2026-11-27 for all 12,989 of them (582k characters), translated in chunks with the English line beside each
meaning, then checked by script and read in samples. What holds them, and what checks them:

- **Where.** The content's meanings in the content areas (`content/chunks`, `content/sentences`, `content/benchmark`,
  bundle `content`); the town's in `town/<area>-meaning.ts` (bundle `town`); Westbay's in a bundle of their own, `city`
  (`city/jobs`, `city/seasons`, `city/talks`, `city/episodes`), loaded with the city (`features/town/TownRoute.tsx`
  `withDictionary('city', …)`; the admin page loads it too). `scripts/i18n-scan.mjs` knows the bundle: `bundleOfArea`
  ('town/city' strings see `city`), `visibleBundles('city')`. The chunks are split by kind in `vite.config.ts`
  (`en-town-arcs`, `en-town-romance`, `en-town-talk`, `en-city-jobs`, `en-city-seasons`, `en-city-talks`, `en-city`) so
  none passes 500 kB.
- **How they read.** A plain paraphrase in the line's register; names, places, numbers and times stay. Where the town
  makes a wrong answer by rule from the line's meaning (`core/town/soundAlike.ts`: him ↔ them, -teen ↔ -ty), the English
  meaning keeps that one word or number, so the same wrong answer is made in English. Clock times in a meaning are
  digits ("5:30"). Phrase cards explain with the English respelling, never the Vietnamese sound hint.
- **Checks.** `coverage.test.ts` demands English for every class now. `meaning.test.ts`: every written answer group
  (`options`, a choice's `intent` labels: `answerGroups()` in the scan tool) has English and stays different; quick
  chats and episodes give different English options for every line; every rule-made sound-alike is still made in
  English; meanings filled in at run time (a job line's `{time}`, the scanner's lines, the asset reports) come out in
  English: the code looks the template up with `tr()` before it fills it.
- **A meaning with a value in it** keeps its placeholder in the English (`{time}`, `{kid}`, `{name}`, `{road}` …); the code
  translates first and fills after (as `StoryChat.tsx` and `romance.ts` already did).

## 5. State

See AGENTS.md §9 "Interface language" for what has English, what does not yet, and the counts.

Known limits:
- Keys are global inside the bundles loaded together, so one Vietnamese string has one English text. Where a word
  needed two (e.g. "Thu nhỏ": zoom out on the map, exit full screen on the button), the code branches on `getLang()`.
  Short keys ('Còn', 'thành', 'Nếu', 'Có', 'Lại', 'Được'…) are fragments of JSX sentences broken by an inline element;
  a new use of the same fragment in another sense needs a whole `tl` sentence instead.
- `tl` translates its string values (labels passed in); a name or text the learner typed goes in as `asIs(value)`.
- A few labels are stored in Vietnamese and translated when shown: the sync device label, the checkup `voiceName`,
  media titles made from a file or a YouTube id ("Video YouTube …" stays as stored).
- A celebration queued before a language switch, and cloud error notices already on screen, stay in the old language
  until they are replaced.
- Bay FM's bulletin (`core/town/radio.ts`, `radioTraffic.ts`) builds its meanings from pieces at run time (`fill`,
  joins with Vietnamese commas, `laterVi`, `partOfDayVi`): every piece has an English entry, but the composed meaning is
  not a key, so in English mode it shows in Vietnamese until the composition looks each piece up with `tr()` (in
  Vietnamese mode `tr` returns its input, so the change cannot touch the Vietnamese).
- Ôn tập loads only `ui` and `content`: a review card of a town or Westbay line (`talk:…`) shows its meaning in
  Vietnamese in English mode unless the town page was opened first.
- The meanings were written by a model (Sonnet) and read only in samples (about 30 per dictionary area); a few add a
  small detail the Vietnamese does not have ("my late husband", "older sister").
- `window.i18nMisses()` (dev server) lists what English mode showed untranslated; it also lists English text that
  quotes a Vietnamese sound hint ("ơ", "ư"), which is expected.
